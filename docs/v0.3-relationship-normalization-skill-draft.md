## 1. 目标

这个 skill 的目标不是“补出尽可能多的边”，而是：

- 收敛关系方向
- 去掉明显噪声边
- 只保留当前 runtime 支持的关系类型
- 确保关系端点能在当前实体集合中闭合
- 把不适合当前 runtime 的语义压回文本字段，而不是生造非法关系

---

## 2. 非目标

这个 skill **不负责**：

- 创造 schema 之外的新关系类型
- 强行恢复完整 BOM 层级
- 强行补全所有对象指向
- 自动生成未来 v0.3 才支持的 `LEADS_TO / TARGET_PART / RELATED_EVENT / RELATED_PART`

---

## 3. 当前 runtime 允许的关系

第一阶段只建议输出当前系统已支持的关系：

- `HAS_8D_REPORT`
- `RELATED_FAILURE_MODE`
- `ROOT_CAUSE`
- `CORRECTIVE_ACTION`
- `PREVENTIVE_ACTION`
- `VERIFIES_CAUSE`
- `HAPPENED_ON`
- `RELATED_SERIAL`
- `AFFECTED_PRODUCT`
- `AFFECTED_SERIAL`
- `RESPONSIBLE_ORG`
- `TARGET_PRODUCT`
- `TARGET_SERIAL`
- `INSTALLED_ON`
- `SUPPLIED_BY`

不在这份清单里的关系，即使从 v0.3 目标层看是合理的，当前也不要直接输出到最终 JSON。

---

## 4. 归一原则

### 4.1 显式关系优先于推断关系

如果文本已经明确给出关系：

- 优先保留显式关系
- 后处理只做字段名、方向和 rel_type 的收敛

### 4.2 单一候选才允许保守补边

如果某类目标实体有多个候选，默认不做“全连接式补边”。

例如：

- 多个 `Organization` 时，不要把所有组织都挂成 `RESPONSIBLE_ORG`
- 多个 `FailureMode` 时，不要把每个 `CauseItem` 都连到所有失效模式
- 多个 `ProductInstance` 时，不要把每个 `PartSerial` 都连到所有实例

### 4.3 关系方向必须 canonical

统一采用当前 runtime 已确定的方向，不输出反向边。

### 4.4 端点必须闭合

只有当 `from_key / to_key` 都能在当前实体集合中找到时，关系才可保留。

### 4.5 关系不足时宁缺毋滥

图质量优先于召回率。  
关系不明确时，宁可少一条边，也不要引入一条错误边。

---

## 5. 当前推荐冻结值（待共创确认）

如果没有新的业务约束，我建议先按下面这些默认值冻结：

1. `HAS_8D_REPORT / ROOT_CAUSE / CORRECTIVE_ACTION / PREVENTIVE_ACTION` 可保守补边
2. `RESPONSIBLE_ORG / RELATED_FAILURE_MODE / HAPPENED_ON / RELATED_SERIAL / SUPPLIED_BY / INSTALLED_ON / VERIFIES_CAUSE` 只有在单一候选或文本明确时才补边
3. 任何多候选场景都不允许“全连接式推断”
4. 不支持的关系语义先回落到 `title / summary / evidence`
5. 显式关系永远优先于代码推断关系

按这套默认值，图谱质量会比“尽量多连边”更稳，也更适合作为 v0.3 过渡阶段的基线。
