## 1. 目标

这个 skill 的目标不是把 D2 文本整段复述，而是把“发生了什么、发生在什么对象上、表现为什么现象、是否已有标准化失效模式”压缩成当前 runtime 能稳定落地的事件主线：

- 是否存在一个明确的 `ProductEvent`
- 事件属于故障 / 异常 / 客诉 / 试验中的哪一类
- `symptom` 应如何以最小歧义保留下来
- 哪些产品实例、序列件、失效模式与该事件明确相关
- 事件与 8D 报告之间是否构成稳定闭环

---

## 2. 非目标

这个 skill **不负责**：

- 重做 D4 根因归类
- 重做 D5 措施抽取
- 输出 `Person`
- 输出 `REPORTED_BY_PERSON / REPORTED_BY_ORG`
- 输出 `RELATED_PART`
- 输出 raw 时间字段或 `timePrecision`
- 输出 `Installation`
- 从模糊 reporter 文本里强行创造组织实体关系

这些内容交给其他 skill、后处理层，或后续 schema 升级。

## 3. 输入边界

### 3.1 章节范围

默认处理：

- D2 问题描述
- 故障描述 / 故障现象
- 客诉 / 投诉信息
- 异常 / 试验失败 / 测试异常
- 与事件主线相关的故障清单、时间、上报、状态描述

### 3.2 `chunk_role` 范围

默认接收：

- `evidence`
- `conclusion`

默认不处理：

- 纯 `background`
- 纯 `metadata`
- 明显属于根因推理的 `hypothesis`
- 明显属于措施描述的 `action`

### 3.3 上下文依赖

允许只读引用：

- 已抽取的 `EightDReport`
- 已抽取的 `FailureMode`
- 已抽取的 `ProductInstance`
- 已抽取的 `PartSerial`

原则：

- 只有文本明确指向某个对象时才建立关系
- 不因为上下文中存在某个实体就默认挂边

### 3.4 与 Foundation 技能的边界

`8d-d2-event-extraction` 默认建立在两个 Foundation 技能之上：

- `8d-actor-entity-typing`
- `8d-temporal-normalization`

边界建议如下：

- `reporterName` 始终先保留原始字符串
- `occurredAt` 只在能高置信标准化时写入规范字段
- 对“公司名 / 部门名 / 人名”的内部判别可以参与推理，但当前 runtime 不直接输出 `Person` 或 reporter 关系

## 4. 输出边界

### 4.1 允许输出的实体

- `ProductEvent`
- `FailureMode`
- 条件性 `ProductInstance`
- 条件性 `PartSerial`
- 条件性 `Organization`

### 4.2 条件性输出的关系

- `ProductEvent -> HAS_8D_REPORT -> EightDReport`
- `ProductEvent -> HAPPENED_ON -> ProductInstance`
- `ProductEvent -> RELATED_SERIAL -> PartSerial`
- `ProductEvent -> RELATED_FAILURE_MODE -> FailureMode`

### 4.3 当前 runtime 先不直接输出的内容

- `Person`
- `REPORTED_BY_PERSON`
- `REPORTED_BY_ORG`
- `RELATED_PART`
- `RESPONSIBLE_ORG`
- raw 时间字段
- `timePrecision`

### 4.4 最小输出 Contract

建议 D2 skill 的最小输出遵循以下规则：

- `ProductEvent`
  - 必填：`eventType`、`symptom`、`confidence`、`supporting_chunks`
  - 推荐：`severity`、`status`、`reporterName`、`occurredAt`
- `FailureMode`
  - 至少提供 `modeName`
  - 若可判断，补 `modeCode`
- `ProductInstance / PartSerial`
  - 只有在对象能稳定闭合时才创建
- 主线关系
  - 必填：`confidence`、`supporting_chunks`

## 5. ProductEvent 抽取规则

### 5.1 是否创建 ProductEvent

只有当文本满足以下至少一项时，才创建 `ProductEvent`：

- 明确描述了一次故障 / 异常 / 客诉 / 试验事件
- 明确出现了“何时何地何对象发生了什么问题”的叙述
- 文本能稳定回答“本份 8D 报告到底在处理哪件事”

以下情况不要单独创建 `ProductEvent`：

- 纯根因解释
- 纯措施清单
- 只有产品背景，没有事件发生
- 只有检测数值，没有事件语义

### 5.2 eventType 判定规则

当前默认枚举仍收敛到：

- `故障`
- `异常`
- `客诉`
- `试验`

推荐映射：

- 现场失效、功能失常、泄漏、裂纹等 -> `故障`
- 生产、装配、测试过程中的偏差 -> `异常`
- 明确来自客户投诉 / 索赔 / 反馈 -> `客诉`
- 台架、出厂、验证、实验中的失败 -> `试验`

如果文本无法稳定归类：

- 选择最保守且最贴近原文的类型
- 不要为了枚举完整强行猜测

### 5.3 symptom 写法

`ProductEvent.symptom` 应尽量：

- 保留客观现象
- 简洁
- 避免混入原因或措施

例如：

- `阀门密封面渗油`
- `装机三个月后弹簧裂纹`
- `出厂试验时压力波动超差`

不要把以下内容直接塞进 `symptom`：

- 根因结论
- 纠正措施
- 主观推测

## 6. 关系规则

### 6.1 HAS_8D_REPORT

只要当前上下文里同时存在 `ProductEvent` 与 `EightDReport`，且文本明确这份报告就是在处理该事件，就允许输出：

- `ProductEvent -> HAS_8D_REPORT -> EightDReport`

### 6.2 HAPPENED_ON

只有当文本明确给出产品实例、序列号、资产号或上下文能稳定闭合到唯一 `ProductInstance` 时，才输出：

- `ProductEvent -> HAPPENED_ON -> ProductInstance`

### 6.3 RELATED_SERIAL

只有当文本明确给出零件序列号 / 批次信息，或上下文能稳定闭合到唯一 `PartSerial` 时，才输出：

- `ProductEvent -> RELATED_SERIAL -> PartSerial`

### 6.4 RELATED_FAILURE_MODE

只有当文本明确出现标准化失效模式，或能高置信映射到已有 `FailureMode` 时，才输出：

- `ProductEvent -> RELATED_FAILURE_MODE -> FailureMode`

如果只是现象，还没形成失效模式名：

- 优先保留在 `symptom`
- 不要为了补边强造 `FailureMode`

---

## 7. Actor / Organization / 时间规则

### 7.1 reporterName

- 始终先保留原始字符串
- 即使内部判断更像 `Organization`，当前 runtime 也不直接输出 reporter 关系

典型保守策略：

- `吴重人` -> 先留在 `reporterName`
- `克诺尔苏州` -> 先留在 `reporterName`
- 不因为 reporter 字段像公司名，就单独创建 `Organization`

### 7.2 Organization

当前阶段只有在组织主体本身就是事件语义中的核心对象时，才考虑输出 `Organization`：

- 明确的客户单位
- 明确的供应商单位
- 明确的责任部门或责任公司

如果组织只出现在 reporter / 联系人位置：

- 优先保留在原始字符串字段
- 不强行建 `Organization`

### 7.3 occurredAt

- 只有高置信日期 / 日期时间才写 `occurredAt`
- 只有年月、相对时间、模糊时间时，当前阶段宁可留空

例如：

- `2026-04-10` -> 可以标准化
- `4 月上旬` -> 当前 runtime 不硬写规范时间
- `装机三个月后` -> 当前 runtime 不硬写规范时间

## 8. 与 D4 / D5 的边界

### 8.1 与 D4 的边界

如果一句话同时包含现象和原因：

- 事件现象部分交给 D2
- 原因推理部分交给 D4

例如：

- `阀门密封面渗油，原因怀疑为 O 型圈硬度不足`
  - `阀门密封面渗油` 留在 D2
  - `O 型圈硬度不足` 留在 D4

### 8.2 与 D5 的边界

如果一句话同时包含事件和措施：

- 事件现象部分交给 D2
- 措施动作部分交给 D5

例如：

- `现场发现泄漏后立即隔离同批次产品`
  - `现场发现泄漏` 留在 D2
  - `隔离同批次产品` 留在 D5

## 9. 当前推荐冻结值（待共创确认）

如果没有新的业务约束，我建议先按下面这些默认值冻结：

1. D2 只负责事件主线，不碰 D4 因果链和 D5 措施链
2. `ProductEvent` 只有在文本明确描述“发生了什么事件”时才创建
3. `reporterName` 先保留 raw，不直接输出 `Person` 或 reporter 关系
4. `Organization` 只有在它本身是事件语义核心对象时才创建
5. `FailureMode` 只有在标准化失效模式足够明确时才创建
6. `HAPPENED_ON / RELATED_SERIAL / RELATED_FAILURE_MODE` 只在映射稳定时输出
7. `occurredAt` 先保守标准化，精度不足时留空
