# v0.3 Actor Entity Typing · Person / Organization 判别规则

**状态**：draft  
**日期**：2026-05-18  
**定位**：定义 v0.3 阶段 actor 类实体的判别与双轨输出规则，目标是减少“人名 / 公司名 / 部门名”混淆。

## 1. 设计目标

本规则解决以下高频错误：

- `reporterName: "克诺尔苏州"` 被误认为是人名
- `reporterName: "吴重人"` 被误认为是组织
- `ownerName: "质量部"` 无法区分是部门还是个人
- `operatorName: "客户QA"` 被误判为具体个人

目标不是“所有 actor 都强制建实体”，而是：

- 原始字段保留
- 明确能判定时再建立 `Person / Organization`
- 不确定时不强行归类

---

## 2. 双轨输出原则

所有 actor 类字段统一采用双轨模式：

1. **原始字段始终保留**
   例如：
   - `reporterName`
   - `ownerName`
   - `operatorName`

2. **规范实体只在高置信时建立**
   例如：
   - `REPORTED_BY_PERSON`
   - `REPORTED_BY_ORG`
   - `OWNED_BY_PERSON`
   - `OPERATED_BY_PERSON`

3. **不确定时默认只保留原始字段**

这是 v0.3 actor typing 的核心保守策略。

---

## 3. 当前适用位置

第一阶段主要覆盖以下位置：

- `ProductEvent.reporterName`
- `EightDReport.ownerName`
- `ActionItem.ownerName`
- `Installation.operatorName`

其他位置如 `manufacturerName / supplierName / ownerName(customer)` 暂按 `Organization` 侧优先处理。

---

## 4. 判别总流程

`8d-actor-entity-typing` 建议按下面顺序执行：

1. **先保留原始字段**
   无论后续能否判定，`reporterName / ownerName / operatorName` 都先完整保留。
2. **先判明显组织 / 部门**
   只要字符串或上下文有强组织信号，优先判为 `Organization`。
3. **再判明显个人**
   在不存在强组织信号时，再判断是否为 `Person`。
4. **同时出现人 + 组织时拆开**
   若同一局部片段里同时出现个人和组织，允许同时输出两个实体，但关系要按字段语义决定。
5. **仍不确定就降级为 unknown**
   保留原始字段，不建规范实体关系。

这个顺序的目的，是先压住“公司 / 部门误判成个人”的高频错误。

---

## 5. Person 判定规则

### 5.1 Person 强信号

以下情况优先判为 `Person`：

- 典型中文姓名
- 姓名 + 职位/称谓
- 人名后带联系方式
- 上下文明确写“责任人 / 联系人 / 操作人 / 审核人 / 报告人”

常见例子：

- `吴重人`
- `张工`
- `王经理`
- `李主任`
- `责任人：张工`
- `联系人：吴重人`

如果仅有一个人名，且没有任何组织化后缀，默认倾向 `Person`。

### 5.2 Person 的保守处理

- 如果 `张工 / 王经理 / 李主任` 这类表达无法稳定拆出“姓名”和“职务”，第一阶段允许直接把完整表达放进 `personName`
- `title` 只有在文本明确且可分离时再单独填充
- 不为了结构完整而强行把称谓拆成不可信的姓名

### 5.3 不应判为 Person 的常见反例

以下情况默认不判为 `Person`：

- 含明显组织后缀
- 只出现部门 / 班组 / 供应商 / 客户单位
- 只有角色代号而无个人识别，如 `客户QA`
- 明显是团队或组织化主体，如 `项目组`

---

## 6. Organization / Department 判定规则

### 6.1 Organization 强信号

以下情况优先判为 `Organization`：

- 含公司/厂/部/科/组/中心/供应商/客户等组织特征词
- 明显为企业、部门、项目组、客户单位、供应商单位
- 语义主体明显不是个人

常见例子：

- `克诺尔苏州`
- `克诺尔制动系统（苏州）有限公司`
- `质量部`
- `制造部`
- `客户QA`
- `苏州某密封件供应商`
- `项目组`

### 6.2 Department 的处理

在 v0.3 第一阶段，**部门不单独建 `Department` 实体**，统一并入 `Organization`：

- `质量部` -> `Organization`
- `制造部` -> `Organization`
- `售后服务组` -> `Organization`

建议通过 `orgType=department` 或等价字段表达其部门属性。

### 6.3 不应判为 Organization 的常见反例

以下情况默认不单独判为 `Organization`：

- 典型个人姓名
- 单独出现的个人称谓且上下文明确指向个人
- 与个人姓名同时出现、但只是个人附带职务描述的短语

---

## 7. 冲突与降级规则

### 7.1 同时出现人和组织

如果文本形如：

- `吴重人（克诺尔苏州）`
- `责任人张工，质量部`

则允许：

- 保留原始字段
- 抽 `Person`
- 抽 `Organization`
- 在信息明确时加 `Person -> BELONGS_TO_ORG -> Organization`

但主关系应优先跟随字段语义：

- `reporterName` / `ownerName` / `operatorName` 若明确指向个人，主关系优先连 `Person`

### 7.2 不允许同时给同一原始值建冲突主关系

如果一个原始值本身就是同一 span，例如：

- `reporterName = "吴重人"`

则不应同时输出：

- `REPORTED_BY_PERSON`
- `REPORTED_BY_ORG`

除非文本明确同时给出了两类主体，且它们是不同对象。

### 7.3 Installation 的特殊保守规则

`Installation.operatorName` 第一阶段只支持：

- 明确个人 -> `OPERATED_BY_PERSON`
- 不确定 -> 仅保留 `operatorName`

即使原始值更像组织或班组，也默认不额外创建组织关系，避免过早引入不稳定语义。

### 7.4 无法稳定判别时的降级

以下情况默认降级为 `unknown`：

- 过短且无上下文的字符串
- 既可能是人名又可能是公司简称
- 只出现代号或缩写
- 角色信息与主体身份冲突

处理策略：

- 保留原始字段
- 不建立 actor 实体关系
- 等后处理或人工审核再决定

## 8. 输出 Contract

建议 `8d-actor-entity-typing` 至少输出以下信息：

- `rawValue`
- `typedAs`
  - `person`
  - `organization`
  - `unknown`
- `confidence`
- `supporting_chunks`
- `relationLabel`
  - `REPORTED_BY_PERSON`
  - `REPORTED_BY_ORG`
  - `OWNED_BY_PERSON`
  - `RESPONSIBLE_ORG`
  - `OPERATED_BY_PERSON`

如判为 `Person`，建议补：

- `personName`
- `title`（可选）
- `email`（可选）
- `phone`（可选）

如判为 `Organization`，建议补：

- `orgName`
- `orgType`
- `orgCode`（若文本明确出现）

如判为 `unknown`：

- 仅保留 `rawValue`
- 不输出 `relationLabel`

---

## 9. 关系建立规则

### 9.1 ProductEvent

- 明确是个人：
  - `ProductEvent -> REPORTED_BY_PERSON -> Person`
- 明确是组织：
  - `ProductEvent -> REPORTED_BY_ORG -> Organization`
- 不确定：
  - 仅保留 `reporterName`

### 9.2 EightDReport

- 明确是个人：
  - `EightDReport -> OWNED_BY_PERSON -> Person`
- 责任部门/责任公司：
  - `EightDReport -> RESPONSIBLE_ORG -> Organization`
- 不确定：
  - 仅保留 `ownerName`

### 9.3 ActionItem

- 明确是个人：
  - `ActionItem -> OWNED_BY_PERSON -> Person`
- 明确是组织：
  - `ActionItem -> RESPONSIBLE_ORG -> Organization`
- 不确定：
  - 仅保留 `ownerName`

### 9.4 Installation

- 明确是个人：
  - `Installation -> OPERATED_BY_PERSON -> Person`
- 不确定或更像组织：
  - 仅保留 `operatorName`

---

## 10. 置信度建议

建议采用保守阈值：

- `0.90 - 1.00`
  - 明确全名 / 明确组织名 / 上下文显式说明身份
- `0.75 - 0.89`
  - 姓名 + 称谓 / 部门名称 / 有较强上下文支持
- `0.55 - 0.74`
  - 有倾向但仍有歧义，通常只保留原始字段，不建主关系
- `< 0.55`
  - 视为 `unknown`

默认建议：

- `confidence >= 0.75` 才允许建立 actor 主关系

---

## 11. Person 与 Organization 的从属关系

`Person -> BELONGS_TO_ORG -> Organization`

只在以下情况建立：

- 文本显式给出个人所属组织
- 同一片段内同时出现“人 + 组织”的明确搭配
- 不是仅靠常识猜测

若只有人名，未给组织，不建立该边。

## 12. 示例判定

### 示例 1

输入：

- `reporterName = "克诺尔苏州"`

输出建议：

- 原始字段保留
- 建 `Organization`
- `ProductEvent -> REPORTED_BY_ORG -> Organization`
- 不建 `Person`

### 示例 2

输入：

- `reporterName = "吴重人"`

输出建议：

- 原始字段保留
- 建 `Person`
- `ProductEvent -> REPORTED_BY_PERSON -> Person`
- 不建 `Organization`

### 示例 3

输入：

- `ownerName = "质量部"`

输出建议：

- 原始字段保留
- 建 `Organization`
- `orgType=department`
- 如上下文明确是报告责任部门，可建 `RESPONSIBLE_ORG`

### 示例 4

输入：

- `operatorName = "客户QA"`

输出建议：

- 原始字段保留
- 若无法明确到具体组织名称，则先不建 `Person`
- 默认也不建立 `OPERATED_BY_PERSON`
- 是否补建 `Organization` 交由后处理或后续阶段决定

### 示例 5

输入：

- `ownerName = "吴重人（克诺尔苏州）"`

输出建议：

- 原始字段保留
- 建 `Person`
- 建 `Organization`
- `EightDReport -> OWNED_BY_PERSON -> Person`
- `Person -> BELONGS_TO_ORG -> Organization`

---

## 13. 与后处理的分工

### 13.1 Skill 负责

- 做保守的一次判别
- 只在高置信时建 `Person / Organization`
- 给出最小 actor relation

### 13.2 后处理负责

- 跨报告的人名归一
- 人员与组织的长期对齐
- 同名不同人的消歧
- 公司简称/全称统一
- 组织类型细化与层级整理

---

## 14. 默认执行口径

在没有进一步共创前，默认策略是：

1. 对 actor 字段先保留原始文本
2. 强组织信号优先于弱个人猜测
3. 明显是个人才建 `Person`
4. 明显是公司/部门/客户/供应商才建 `Organization`
5. 不确定时不建规范实体关系
6. 绝不为了“图谱完整”强行把模糊主体塞进 `Person`

这条默认口径比“多建一些实体”更稳。
