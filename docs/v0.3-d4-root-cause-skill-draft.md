## 1. 目标

这个 skill 的目标不是“重述 D4 章节”，而是把 D4 里的根因信息压缩成可入图的最小事实单元：

- 哪些原因项被报告明确认为与问题相关
- 这些原因项属于 `直接原因 / 中间原因 / 根本原因` 中的哪一类
- 哪些失效模式、部件、事件与这些原因项有关
- 在证据足够明确时，原因项之间是否存在 `LEADS_TO` 因果链

---

## 2. 非目标

这个 skill **不负责**：

- 抽取 D3 / D5 / D7 措施项
- 恢复完整 BOM 树
- 自动推断所有安装历史
- 对弱证据文本强行创造完整因果链
- 生成最终业务键
- 统一 taxonomy 编码

这些内容交给其他 skill 或后处理模块。

## 3. 输入边界

### 3.1 章节范围

默认处理以下内容：

- D4 根因分析主章节
- D4 下属证据章节，如：
  - 断口分析
  - 金相检测
  - 硬度试验
  - 化学成分分析
  - 对比实验分析
  - 加速老化试验
  - 排查结论
  - 失效机理分析

### 3.2 `chunk_role` 范围

默认接收：

- `evidence`
- `hypothesis`
- `conclusion`

默认不处理：

- `action`
- `background`
- `metadata`

### 3.3 上下文依赖

允许读取以下上游上下文作为只读参考：

- 已解析出的 `EightDReport`
- 已解析出的 `ProductEvent`
- 已解析出的 `ProductInstance`
- 已解析出的 `PartSerial`
- 已解析出的 `BOMPart`
- 已解析出的表格/检测结论摘要

原则：

- 可以**引用已有实体**来建立关联
- 不能在没有文本证据的情况下，仅因为上下文存在就强行建边

### 3.4 与 Foundation 技能的边界

`8d-d4-root-cause-extraction` 默认建立在两个 Foundation 技能之上：

- `8d-actor-entity-typing`
- `8d-temporal-normalization`

边界建议如下：

- D4 **不直接产出 `Person`**
- 如 D4 文本明确指向责任部门 / 供应商 / 客户单位，可条件性输出 `Organization`
- 时间表达仅作为原因语义和证据的一部分使用，不在 D4 阶段直接产出规范时间字段
- 若时间顺序对因果链有帮助，只允许体现在 `LEADS_TO.sequence_order` 或 `evidence` 中

## 4. 输出边界

### 4.1 允许输出的实体

- `CauseItem`
- `FailureMode`
- `Organization`
  仅当 D4 文本明确指向责任部门、责任公司、供应商或客户单位时条件性输出。

### 4.2 条件性输出的关系

- `EightDReport -> ROOT_CAUSE -> CauseItem`
- `EightDReport -> RESPONSIBLE_ORG -> Organization`
- `CauseItem -> RELATED_FAILURE_MODE -> FailureMode`
- `CauseItem -> RELATED_PART -> BOMPart`
- `CauseItem -> RELATED_SERIAL -> PartSerial`
- `CauseItem -> RELATED_EVENT -> ProductEvent`
- `CauseItem -> LEADS_TO -> CauseItem`

### 4.3 不允许输出的内容

- `ActionItem`
- `Installation`
- `Person`
- 规范时间字段
- raw 时间字段
- 反向边
- 派生边
- 仅凭常识补出的原因

### 4.4 最小输出 Contract

建议 D4 skill 的最小输出遵循以下规则：

- `CauseItem`
  - 必填：`title`、`causeType`、`confidence`、`supporting_chunks`
  - 推荐：`evidence`、`isVerified`
- `FailureMode`
  - 至少提供 `modeName` 或 `modeCode`
- `Organization`
  - 至少提供 `orgName`
  - 若可判断，补 `orgType`
- `LEADS_TO`
  - 必填：`confidence`、`supporting_chunks`
  - 可选：`sequence_order`

---

## 5. CauseItem 抽取规则

### 5.1 是否创建 CauseItem

只有当文本满足以下至少一项时，才创建 `CauseItem`：

- 明确被报告认定为原因
- 被证据链强支持，且语义上属于因果解释的一部分
- 被明确列为“直接原因 / 中间原因 / 根本原因”

以下情况**不创建** `CauseItem`：

- 纯现象描述
- 纯检测结果但未指向因果解释
- 被明确排除的假设原因
- 仅有模糊猜测且无后续支持

### 5.2 原因粒度

默认原则：**一个 CauseItem 只表达一个最小可理解原因单元**。

例如：

- “O 型圈硬度低于图纸要求，且来料检验未覆盖硬度项”
  建议拆成两个 CauseItem：
  - `O 型圈硬度低于图纸要求`
  - `来料检验未覆盖硬度项`

不建议把多个原因揉成一个长句 title。

### 5.3 title 写法

`title` 应尽量是：

- 简短
- 可复用
- 去掉报告口吻
- 保留技术事实

建议：

- 用短语，不用整段复述
- 尽量避免“经分析认为”“判断为”“初步确认”等套话

### 5.4 复合句拆分优先级

如果一个句子同时包含多类信息，建议按下面顺序拆分：

1. **原因 + 证据**
   - 原因进入 `CauseItem.title`
   - 检测/试验/对比结果进入 `evidence`
2. **原因 + 措施**
   - D4 只保留原因部分
   - 措施部分留给 D5 / D7
3. **原因 + 组织主体**
   - 若明确是责任部门/责任公司，可条件性输出 `Organization`
   - 不建立 `Person`
4. **原因 + 时间表达**
   - 时间短语保留在 `evidence`
   - 不直接产出规范时间字段
5. **原因 + 否定候选**
   - 被否定的那部分不创建 `CauseItem`

## 6. causeType 判定规则

### 6.1 默认枚举

- `直接原因`
- `中间原因`
- `根本原因`

### 6.2 判定口径

#### 直接原因

离故障现象最近、直接触发问题的机制或状态。

例：

- 密封面失效
- 弹簧断裂
- 接触不良

#### 中间原因

连接现象和深层根因之间的桥接环节。

例：

- 热处理后硬度不足导致疲劳寿命下降
- 装配偏差导致局部应力集中

#### 根本原因

最底层、最应被治理、通常具有可改进责任归属的原因。

例：

- 供应商热处理参数失控
- 来料检验未覆盖关键硬度项
- 设计公差定义不合理

### 6.3 默认策略

如果报告没有明确分层、只给出一个最终原因结论，则默认标记为：

- `根本原因`

如果文本明确存在因果层级，再拆成：

- 靠近症状的一层 → `直接原因`
- 中间桥接层 → `中间原因`
- 最底层治理原因 → `根本原因`

---

## 7. 失败模式与对象关联规则

### 7.1 FailureMode

只有在文本明确提到失效模式时，才输出 `FailureMode`。

可接受来源：

- 章节标题
- 明确的失效术语
- 检测/结论中的标准化故障名称

### 7.2 与 Part / Serial / Event 的关联

以下关系只在**目标实体已在上下文中存在，且文本明确指向它**时输出：

- `CauseItem -> RELATED_PART -> BOMPart`
- `CauseItem -> RELATED_SERIAL -> PartSerial`
- `CauseItem -> RELATED_EVENT -> ProductEvent`

如果文本只说“该零件”“该阀门组件”“该批次件”，但无法稳定映射到已知实体：

- 不强行输出关系
- 把事实留在 `title/evidence` 中，交给后处理或 relationship normalization

### 7.3 Organization 的条件性输出

只有在 D4 文本明确把责任归到组织主体时，才建议输出 `Organization`。

适合的例子：

- `供应商热处理参数失控`
- `质量部检验规范未覆盖关键硬度项`
- `客户现场维护流程不当`

建议做法：

- 输出 `Organization`
- 如文本明确是报告责任归属，可补：
  - `EightDReport -> RESPONSIBLE_ORG -> Organization`

不适合的情况：

- 只有流程名、岗位名、模糊责任短语
- 只是“来料检验未覆盖硬度项”这类未明确到组织主体的表述

这类情况先留在 `CauseItem.title/evidence`，不要强行建 `Organization`。

### 7.4 Actor / Temporal 边界

在 D4 中：

- 即使句子里出现个人姓名，也不直接产出 `Person`
- 如果时间表达只是帮助解释顺序或背景，优先保留在 `evidence`
- 例如：
  - `装机三个月后出现裂纹`
  - `2026年5月批次件热处理异常`

这些时间信息可以帮助理解根因，但不在 D4 skill 中直接标准化输出

---

## 8. LEADS_TO 因果链规则

### 8.1 允许输出的前提

只有在满足以下至少一项时，才允许输出 `CauseItem -> LEADS_TO -> CauseItem`：

- 文本出现明确因果词：
  - 导致
  - 造成
  - 进而
  - 使得
  - 结果是
- 文本给出明显的步骤链或顺序链
- 报告明确分层列出“直接原因 / 中间原因 / 根本原因”

### 8.2 不允许输出的情况

以下情况不应强行生成 `LEADS_TO`：

- 只是多个原因并列罗列
- 原因之间没有明确顺序
- 只有一个根因项
- 仅凭行业常识脑补链条

### 8.3 边属性建议

如输出 `LEADS_TO`，建议在 `properties` 中至少带：

- `confidence`
- `supporting_chunks`

如文本有明确顺序，还可加：

- `sequence_order`

---

## 9. 否定语义与排除项规则

### 9.1 明确排除的候选原因

如果文本表达：

- 未见
- 未发现
- 排除
- 不是
- 无证据表明

则默认**不创建**对应 `CauseItem`。

### 9.2 排除信息如何保留

v0.3 第一阶段不把“被排除原因”直接建成 CauseItem。  
这些内容后续可由更细的 `Finding` / `Hypothesis` 模型承接。

当前策略：

- 不建 CauseItem
- 不建 `LEADS_TO`
- 不因为排除文本降低其他已验证根因的置信度

---

## 10. 置信度规则

### 10.1 建议区间

- `0.90 - 1.00`
  - 文本明确写为根因/直接原因/中间原因
  - 且有实验/检测/验证结果支持

- `0.75 - 0.89`
  - 结论明确，但验证证据较弱或间接

- `0.55 - 0.74`
  - 仍处于推断/分析阶段，未完全验证

- `< 0.55`
  - 原则上不建议输出为正式 CauseItem

### 10.2 isVerified 判定

只有在文本明确出现这些语义时，`isVerified=true`：

- 已验证
- 已确认
- 试验证明
- 检测证明
- 复现确认

其余情况：

- 默认为 `false` 或留空

---

## 11. supporting_chunks 规则

每个 `CauseItem` 必须至少有 1 个 `supporting_chunk`。

推荐：

- 直接结论句 + 证据句同时支持时，保留多个 chunk
- 如果只是图表/检测结果支持，允许引用证据 chunk 而非只引用结论 chunk

如果没有明确 chunk 证据：

- 不输出该 CauseItem

---

## 12. 默认输出口径

### 12.1 一般优先级

优先输出：

- 已被确认的根因
- 与根因直接相关的失效模式
- 能稳定形成因果链的原因层级

慎重输出：

- 仅推测的中间原因
- 无法唯一映射对象的关联关系
- 仅凭章节标题推断出的 FailureMode

### 12.2 与 Action 的边界

如果一句话里同时出现原因和措施：

- 属于“为什么发生”部分 → 留在 D4 skill
- 属于“怎么处理”部分 → 不在本 skill 输出 ActionItem

例如：

- “由于来料检验未覆盖硬度项，后续增加硬度全检”
  - D4 skill 只保留原因部分
  - 措施部分交给 D5/D7 skill

---

## 13. 默认失败策略

当 D4 内容证据不足时：

- 允许输出空结果
- 不要为了“凑满图谱”强行造 CauseItem

当只识别出原因文本但无法稳定归类时：

- 允许输出 `CauseItem`
- `causeType` 默认用最保守策略
- 不输出 `LEADS_TO`

当与已有上下文实体映射不稳定时：

- 先保留原因实体
- 暂不输出对应关系

---

## 14. 当前建议的默认实现

在我们正式拍板前，我建议 D4 skill 先按下面的保守默认值执行：

1. 处理 D4 章节下的 `evidence / hypothesis / conclusion`
2. 输出 `CauseItem / FailureMode / Organization`
3. `Organization` 只在明确责任归属到组织主体时输出
4. 不直接输出 `Person`
5. 不直接输出规范时间字段或 raw 时间字段
6. 仅在文本明确时输出 `LEADS_TO`
7. 被排除的候选原因不建 CauseItem
8. 不能唯一映射对象时不建 `RELATED_PART / RELATED_SERIAL / RELATED_EVENT`
9. 没有 supporting chunk 的原因不输出

---

## 15. 当前推荐冻结值（待共创确认）

如果没有新的业务约束，我建议先按下面这些默认值冻结：

1. 被排除的候选原因 **不入图**
2. 单一最终原因默认记为 `根本原因`
3. `LEADS_TO` 先按**显式因果优先**执行，不靠常识补链
4. 多原因拆分采用“中等偏保守”策略：每个子句能独立回答“为什么发生”时才拆
5. `RELATED_PART / RELATED_SERIAL / RELATED_EVENT` 只在已有目标实体且映射稳定时输出
6. `Organization` 只在责任主体明确时输出，并优先挂到 `EightDReport -> RESPONSIBLE_ORG`
7. 时间表达保留在 `evidence`，暂不在 D4 skill 中单独标准化

按这套默认值，`8d-d4-root-cause-extraction` 已经可以进入接近实现前的规则固化阶段。
