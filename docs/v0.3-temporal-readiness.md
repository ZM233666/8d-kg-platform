## 1. 目标

v0.3 当前不追求“一步到位的完整 temporal KG”，但要提前满足以下条件：

- 关键业务时间字段都采用正确类型
- 关键关系支持未来增加有效期属性
- 当前状态不依赖不可回放的单点字段
- 未来能做时间窗口查询、历史回看和趋势分析

---

## 2. 关键原则

### 2.1 不再新增自由文本时间字段

新的关键时间属性必须优先定义为：

- `date`
- `datetime`

而不是 `Text`。

### 2.2 业务时间与系统时间分离

必须区分：

- 业务时间
  - `reportDate`
  - `occurredAt`
  - `commissionDate`
  - `dueDate`
  - `installTime`
  - `removeTime`
- 系统时间
  - `created_at`
  - `updated_at`

这两类时间不能混用。

### 2.3 当前状态应由历史推导

像：

- 当前安装件
- 当前有效关系
- 当前责任归属

不应只靠单个“当前状态字段”作为唯一事实源。  
应允许从历史记录或有效期关系推导。

### 2.4 关系要为有效期留口

v0.3 阶段即使暂不全面写入，也应预留这些关系属性语义：

- `valid_from`
- `valid_to`
- `confirmed_at`
- `observed_at`
- `created_by`

### 2.5 时间解析不允许强猜

如果文本只有：

- 年月
- 模糊日期
- 相对时间

则不应强行补成精确 `datetime`。  
需要保守标准化，并保留原始文本或精度信息。

---

## 3. 时间字段冻结清单

以下字段在 v0.3 中建议直接冻结类型：

- `EightDReport.reportDate: date | datetime`
- `ProductEvent.occurredAt: datetime`
- `ProductInstance.commissionDate: date | datetime`
- `ActionItem.dueDate: date | datetime`
- `Installation.installTime: datetime`
- `Installation.removeTime: datetime`

以下字段建议冻结为布尔：

- `CauseItem.isVerified`
- `Installation.isCurrent`

补充约束：

- 上述关键时间字段建议默认允许对应的 raw 文本辅助字段，如 `reportDateRaw / occurredAtRaw / dueDateRaw`
- raw 字段用于保留原始表达与时间精度，不替代规范时间字段

---

## 4. 时序关系准备

### 4.1 高优先级关系

这些关系未来最值得增加时间语义：

- `PartSerial -> INSTALLED_ON -> ProductInstance`
- `ProductEvent -> HAPPENED_ON -> ProductInstance`
- `EightDReport -> ROOT_CAUSE -> CauseItem`
- `ActionItem -> VERIFIES_CAUSE -> CauseItem`
- `ActionItem -> TARGET_SERIAL / TARGET_PRODUCT / TARGET_PART`
- `EightDReport -> RESPONSIBLE_ORG`

### 4.2 推荐的未来关系属性

对于上述关系，未来可逐步补充：

- `valid_from`
- `valid_to`
- `confirmed_at`
- `confidence`
- `supporting_chunks`
- `created_by`

说明：

- `created_at` 是系统写入时间
- `confirmed_at` 是业务上被确认的时间
- `valid_from / valid_to` 是业务有效期

三者不能互相替代。

---

## 5. 当前状态与历史状态的边界

### 5.1 Installation

`Installation` 是时序图谱的关键准备实体。

建议：

- `isCurrent` 可以保留为便利字段
- 但真正的当前安装关系应可由：
  - `removeTime is null`
  - 或最新有效区间
  推导得出

也就是说：

- `isCurrent` 不是唯一事实源
- 它只是缓存/便利视图

### 5.2 hasCurrentPart / current ownership

类似：

- `ProductInstance.hasCurrentPart`
- 当前责任组织

都更适合视为派生结果，而不是原始抽取事实。

---

## 6. 时间精度与原始文本保留

为避免返工，建议从 v0.3 起采用：

- 标准化时间字段
- 原始时间文本辅助保留

例如：

- `occurredAt = 2026-05-18T10:30:00Z`
- `occurredAtRaw = "2026年5月18日10:30"`

如果只知道：

- `2026年5月`

则不要强造为某一天的 `datetime`。  
建议：

- `occurredAtRaw = "2026年5月"`
- 标准化字段保守留空
- 在 skill / staging 层记录 `timePrecision = month`

---

## 7. 与抽取 skill 的分工

### 7.1 Skill 负责

- 抽取原始时间表达
- 在高置信时输出标准化时间
- 不强猜精确时刻

### 7.2 `8d-temporal-normalization` 负责

- ISO 标准化
- 时区/精度处理
- 原始文本保留
- `timePrecision` 标记
- 日期和时间边界修复

### 7.3 后处理/Writer 负责

- 关系级时间属性补全
- 当前状态派生
- 时间窗口索引优化

---

## 8. v0.3 最低落地要求

为避免后续返工，至少应做到：

1. 关键时间字段不再用 `Text`
2. `Installation` 作为时序准备实体保留
3. `LEADS_TO / INSTALLED_ON / ROOT_CAUSE / VERIFIES_CAUSE` 等关系为未来有效期属性留口
4. 当前状态由历史可推导，而不是只靠单一便利字段
5. 时间精度不足时保留原始文本，不强猜

只要这五条先守住，后面升级到更完整的 temporal KG 时，返工量会明显下降。
