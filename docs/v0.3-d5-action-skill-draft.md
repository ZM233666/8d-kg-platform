## 1. 目标

这个 skill 的目标不是把 D3 / D5 / D6 / D7 文本整段重述，而是把措施信息压缩成当前能稳定入图的最小执行单元：

- 哪些措施被明确提出或执行
- 这些措施属于 `临时D3 / 纠正D5 / 预防D7` 中的哪一类
- 哪些措施明确用于验证某个原因
- 哪些产品实例、序列件或组织是这些措施的作用对象或责任主体

---

## 2. 非目标

这个 skill **不负责**：

- 重做 D4 根因归类
- 输出 `Person`
- 输出 raw 时间字段或 `timePrecision`
- 自动恢复完整实施过程或执行日志
- 生成当前 runtime 不支持的 `TARGET_PART` / `RELATED_EVENT`

这些内容交给其他 skill 或后续 schema 升级。

---

## 3. 输入边界

### 3.1 章节范围

默认处理：

- D3 临时遏制措施
- D5 永久纠正措施
- D6 实施与验证
- D7 防止再发生
- 相关表格或章节中的措施清单、责任人、完成日期、验证结论

### 3.2 `chunk_role` 范围

默认接收：

- `action`
- `conclusion`
- `evidence`

默认不处理：

- 纯 `background`
- 与措施无关的 `metadata`

### 3.3 上下文依赖

允许只读引用：

- 已抽取的 `EightDReport`
- 已抽取的 `CauseItem`
- 已抽取的 `ProductInstance`
- 已抽取的 `PartSerial`
- 已抽取的 `Organization`

原则：

- 只能在文本明确指向时建立关系
- 不因为上下文存在就强行把每条措施挂到所有原因或所有产品上

### 3.4 与 Foundation 技能的边界

`8d-d5-action-extraction` 默认建立在两个 Foundation 技能之上：

- `8d-actor-entity-typing`
- `8d-temporal-normalization`

边界建议如下：

- D5 **不直接产出 `Person`**
- 负责人优先保留在 `ownerName`
- `dueDate` 只在能高置信标准化时写入规范字段
- 组织责任主体仅在文本明确时输出 `Organization`

## 4. 输出边界

### 4.1 允许输出的实体

- `ActionItem`
- 条件性 `Organization`

### 4.2 条件性输出的关系

- `EightDReport -> CORRECTIVE_ACTION -> ActionItem`
- `EightDReport -> PREVENTIVE_ACTION -> ActionItem`
- `ActionItem -> VERIFIES_CAUSE -> CauseItem`
- `ActionItem -> TARGET_PRODUCT -> ProductInstance`
- `ActionItem -> TARGET_SERIAL -> PartSerial`
- `ActionItem -> RESPONSIBLE_ORG -> Organization`

### 4.3 不允许输出的内容

- `Person`
- `TARGET_PART`
- `RELATED_EVENT`
- raw 时间字段
- `timePrecision`
- 反向边

### 4.4 最小输出 Contract

建议 D5 skill 的最小输出遵循以下规则：

- `ActionItem`
  - 必填：`title`、`actionType`、`confidence`、`supporting_chunks`
  - 推荐：`status`、`ownerName`、`dueDate`
- `Organization`
  - 至少提供 `orgName`
  - 若可判断，补 `orgType`
- `VERIFIES_CAUSE / TARGET_PRODUCT / TARGET_SERIAL / RESPONSIBLE_ORG`
  - 必填：`confidence`、`supporting_chunks`

## 5. ActionItem 抽取规则

### 5.1 是否创建 ActionItem

只有当文本满足以下至少一项时，才创建 `ActionItem`：

- 明确提出要执行的措施
- 明确说明已经执行/完成的措施
- 明确列出防再发动作、检验加强、隔离、返工、替换、培训、流程修订

以下情况不要创建 `ActionItem`：

- 纯根因描述
- 纯现象描述
- 没有动作语义的责任归属
- 只是未来可能考虑、没有形成明确措施的弱建议

### 5.2 title 写法

`title` 应尽量：

- 简短
- 直接体现动作
- 去掉“建议/拟/计划”等口吻噪声

例如：

- `隔离同批次阀门并加严测试`
- `更换为 Viton 材质 O 型圈`
- `来料增加 100% 硬度检验`

### 5.3 复合句拆分优先级

如果同一句同时包含多项动作，建议：

1. 不同责任对象、不同完成日期、不同动作目标时拆分为多个 `ActionItem`
2. 同一动作的实施 + 验证描述，优先保留为一个 `ActionItem`，把验证信息放进上下文或关系中
3. 同一动作的细节补充，优先保留在 `title` 或支持证据中，不机械拆碎

---

## 6. actionType 判定规则

### 6.1 当前默认枚举

- `临时D3`
- `纠正D5`
- `预防D7`

### 6.2 默认映射

- D3 / 临时遏制 / 隔离 / 加严筛查 -> `临时D3`
- D5 / D6 / 永久纠正 / 更换 / 修复 / 参数调整 -> `纠正D5`
- D7 / 防再发 / 标准修订 / 培训 / 检验规范更新 -> `预防D7`

### 6.3 D6 的处理

当前 runtime 不单独建 D6 类型。  
如果文本表达的是 D6 执行或落地动作，默认并入：

- `纠正D5`

---

## 7. 关系规则

### 7.1 VERIFIES_CAUSE

只有在文本明确表达“该措施用于验证 / 消除 / 关闭某原因”时，才输出：

- `ActionItem -> VERIFIES_CAUSE -> CauseItem`

如果只能看出“措施与问题相关”，但不能稳定指向某个已知原因：

- 不强行输出 `VERIFIES_CAUSE`

### 7.2 TARGET_PRODUCT / TARGET_SERIAL

只有当目标实例或序列件在上下文中已存在，且文本明确指向时，才输出：

- `ActionItem -> TARGET_PRODUCT -> ProductInstance`
- `ActionItem -> TARGET_SERIAL -> PartSerial`

### 7.3 RESPONSIBLE_ORG

只有在文本明确给出责任部门 / 责任单位 / 供应商 / 客户单位时，才输出：

- `ActionItem -> RESPONSIBLE_ORG -> Organization`

如果只给出个人负责人或模糊岗位：

- 保留在 `ownerName`
- 不强行输出 `Organization`

---

## 8. 时间与负责人规则

### 8.1 ownerName

- 始终先保留原始字符串
- 即使内部判断更像组织，也不要在当前 runtime 中强行输出 `Person`

### 8.2 dueDate

- 只有高置信日期才写 `dueDate`
- 只有年月 / 相对时间 / 模糊时间时，当前阶段宁可留空

---

## 9. 当前推荐冻结值（待共创确认）

如果没有新的业务约束，我建议先按下面这些默认值冻结：

1. D3 / D5 / D6 / D7 都统一收敛成当前 3 类 `actionType`
2. D6 默认并入 `纠正D5`
3. 一个动作只有在责任对象、完成时间或目标对象明显不同的时候才拆分
4. `VERIFIES_CAUSE` 只在明确指向已知原因时输出
5. `TARGET_PRODUCT / TARGET_SERIAL` 只在映射稳定时输出
6. `RESPONSIBLE_ORG` 只在责任组织明确时输出
7. `ownerName` 先保留 raw，`dueDate` 先保守标准化

按这套默认值，`8d-d5-action-extraction` 就可以进入当前 runtime 可落地的规则固化阶段。
