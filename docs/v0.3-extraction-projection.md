# v0.3 Extraction Projection · Codex 抽取视图

**状态**：draft  
**日期**：2026-05-22  
**定位**：本文件从 [v0.3-target-ontology.md](/Users/God-Prime/Desktop/KnowledgeGraph/8d-kg-platform/docs/v0.3-target-ontology.md) 中投影出一份“适合 Codex skill 直接输出”的收缩 schema 视图。

---

## 1. 设计目标

Codex skill 不直接对完整 ontology 负责，而是只负责输出：

- 文本中可稳定证实的实体
- 文本中可稳定证实的单向关系
- 原始属性值
- 高置信 actor typing 结果
- 最小必要时间字段
- 必要的 `supporting_chunks`

以下内容不由 skill 直接承担：

- 派生关系
- 反向关系
- 最终 business key 拼装
- taxonomy 深度归类
- 安装关系的最终 current state 推断

## 2. v0.3 第一阶段直接抽取实体

### 2.1 直接抽取

- `EightDReport`
- `ProductEvent`
- `CauseItem`
- `ActionItem`
- `FailureMode`
- `Organization`
- `FailureProduct`
- `FailureProductMention`
- `ProductInstance`
- `PartSerial`
- `BOMPart`

### 2.2 条件性抽取

- `Person`
  仅在文本明确指向个人时抽取；如果无法区分人名与公司/部门名，只保留原始字符串字段。
- `ProductModel`
  仅在文档明确给出型号名/型号编码时抽取。
- `Installation`
  仅在文档明确描述装配/拆换动作、且时间与对象足够清晰时抽取。
  若抽取 `Installation`，建议同步保留 `installTime / removeTime` 与对应 raw 时间文本。

### 2.3 暂不要求第一阶段直接抽取

- `EventCategory`
- 更细粒度的产品线 / 产品族 / 产品类别 taxonomy

## 4. 关系投影

### 4.1 第一阶段允许 Codex 直接输出的关系

- `ProductEvent -> HAPPENED_ON -> ProductInstance`
- `ProductEvent -> RELATED_SERIAL -> PartSerial`
- `ProductEvent -> RELATED_PART -> BOMPart`
- `ProductEvent -> RELATED_FAILURE_MODE -> FailureMode`
- `ProductEvent -> RESPONSIBLE_ORG -> Organization`
- `ProductEvent -> HAS_8D_REPORT -> EightDReport`
- `ProductEvent -> REPORTED_BY_PERSON -> Person`
- `ProductEvent -> REPORTED_BY_ORG -> Organization`

- `EightDReport -> ROOT_CAUSE -> CauseItem`
- `EightDReport -> CORRECTIVE_ACTION -> ActionItem`
- `EightDReport -> PREVENTIVE_ACTION -> ActionItem`
- `EightDReport -> RESPONSIBLE_ORG -> Organization`
- `EightDReport -> OWNED_BY_PERSON -> Person`
- `EightDReport -> AFFECTED_PRODUCT -> ProductInstance`
- `EightDReport -> AFFECTED_SERIAL -> PartSerial`
- `EightDReport -> AFFECTED_PART -> BOMPart`

- `CauseItem -> RELATED_FAILURE_MODE -> FailureMode`
- `CauseItem -> RELATED_PART -> BOMPart`
- `CauseItem -> RELATED_SERIAL -> PartSerial`
- `CauseItem -> RELATED_EVENT -> ProductEvent`
- `CauseItem -> LEADS_TO -> CauseItem`

- `ActionItem -> VERIFIES_CAUSE -> CauseItem`
- `ActionItem -> RELATED_EVENT -> ProductEvent`
- `ActionItem -> TARGET_SERIAL -> PartSerial`
- `ActionItem -> TARGET_PRODUCT -> ProductInstance`
- `ActionItem -> TARGET_PART -> BOMPart`
- `ActionItem -> RESPONSIBLE_ORG -> Organization`
- `ActionItem -> OWNED_BY_PERSON -> Person`

- `EightDReport -> MENTIONS_FAILURE_PRODUCT -> FailureProductMention`
- `FailureProductMention -> INSTANCE_OF_FAILURE_PRODUCT -> FailureProduct`

- `Installation -> OPERATED_BY_PERSON -> Person`

### 4.2 建议由后处理补的关系

- `Person -> BELONGS_TO_ORG -> Organization`
- `ProductInstance -> BASED_ON_MODEL -> ProductModel`
- `PartSerial -> INSTANCE_OF_PART -> BOMPart`
- `PartSerial -> INSTALLED_ON -> ProductInstance`
- `Installation -> PRODUCT -> ProductInstance`
- `Installation -> PART_SERIAL -> PartSerial`
- `Installation -> BOM_PART -> BOMPart`
- `Installation -> GENERATED_BY_EVENT -> ProductEvent`
- `ProductModel -> HAS_BOM_ROOT -> BOMPart`
- `ProductModel -> HAS_BOM_PART -> BOMPart`
- `BOMPart -> PARENT_PART -> BOMPart`

原因：

- 这些关系常需要跨多个 chunk 或结合结构化表格/BOM 规则综合推断
- 直接要求 Codex 产出容易不稳定

### 4.3 不建议第一阶段由 Codex 直接产出的关系

- 反向边
- 派生边
- 当前状态类边
- taxonomy 深层父子边
- 治理边（例如 `CHUNK_OF_REPORT`）由 writer / graph-governance 层生成，不由 Codex 直接输出

## 5. Skill 分工建议

### 5.1 `8d-d2-event-extraction`

建议负责：

- `ProductEvent`
- `FailureMode`
- `ProductInstance`
- `PartSerial`
- 条件性 `Organization`
- 事件到产品实例 / 序列件 / 失效模式 / 8D 报告的主线关系

边界：

- 当前 runtime 先不直接输出 `Person`
- `reporterName` 优先保留原始字符串，不直接输出 `REPORTED_BY_PERSON / REPORTED_BY_ORG`
- `occurredAt` 只有高置信才标准化，raw 时间文本继续留在 v0.3 目标层
- 当前 runtime 先只稳定输出 `HAPPENED_ON / RELATED_SERIAL / RELATED_FAILURE_MODE / HAS_8D_REPORT`
- `RELATED_PART` 与事件侧组织关系继续留在 v0.3 目标层或后处理层
- `ProductInstance / PartSerial` 只有在实例级对象能稳定闭合时才创建

### 5.2 `8d-d4-root-cause-extraction`

建议负责：

- `CauseItem`
- `FailureMode`
- 条件性 `Organization`
- `CauseItem -> LEADS_TO -> CauseItem`
- `CauseItem` 与 `ProductEvent / BOMPart / PartSerial` 的关联

边界：

- `Organization` 只在 D4 明确出现责任部门 / 责任公司 / 供应商 / 客户单位时输出
- 同时允许输出明确运营商单位（如地铁运营主体）；推荐标注 `orgType="运营商"`
- 不直接输出 `Person`
- 时间表达留在 `evidence` 或交给 `8d-temporal-normalization`

### 5.3 `8d-d5-action-extraction`

建议负责：

- `ActionItem`
- 条件性 `Organization`
- 条件性 `FailureProductMention`
- `ActionItem -> VERIFIES_CAUSE -> CauseItem`
- `ActionItem` 与 `ProductInstance / PartSerial / BOMPart` 的目标关系

边界：

- 当前 runtime 先不直接输出 `Person`
- `ownerName` 优先保留原始字符串
- `dueDate` 只有高置信才标准化
- 当前 runtime 先只稳定输出 `TARGET_PRODUCT / TARGET_SERIAL`，`TARGET_PART` 继续留在 v0.3 目标层
- 如果动作责任单位明确是运营主体（如“深圳地铁运营集团”），可输出 `Organization(orgType="运营商")`

### 5.4 `8d-actor-entity-typing`

建议负责：

- `Person / Organization` 区分
- `reporterName / ownerName / operatorName` 的双轨输出
- 高置信 actor relation 建立
- 不确定时只保留原始字符串
- 对明显运营主体（地铁/深铁/轨道交通）优先归到 `Organization.orgType="运营商"`

### 5.5 `8d-relationship-normalization`

建议负责：

- 关系方向收敛
- 重复关系去重
- 模糊角色归类
- `rootCause / correctiveAction / preventiveAction` 主线补全

### 5.6 `8d-temporal-normalization`

建议负责：

- `reportDate`
- `occurredAt`
- `commissionDate`
- `dueDate`
- `installTime / removeTime`

规则：

- 尽量标准化为 ISO 日期/时间
- 无法确认精度时留原始文本到辅助字段，如 `reportDateRaw / occurredAtRaw / dueDateRaw`
- skill 不为“只有年月/相对时间”的表达强造精确 `datetime`
- `timePrecision` 建议作为 temporal normalization 的中间元信息保留，第一阶段不要求直接入图

## 6. 第一阶段不做的事情

为了保证 v0.3 第一阶段稳定性，以下内容不建议一上来就让 Codex 承担：

- 全量 BOM 树恢复
- 复杂安装历史回放
- 事件分类体系深度映射
- 大规模人名与组织名的跨报告全局对齐
- 自动生成反向边
- 自动推断所有当前安装件
- 从弱证据文本中生成高置信度业务键
