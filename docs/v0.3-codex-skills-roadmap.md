## 2. 推荐的 Skill 分层

### 2.1 母 skill

`8d-report-extraction-core`

职责：
- 定义全局实体/关系白名单
- 定义通用溯源规则
- 定义占位符过滤规则
- 定义否定语义总原则
- 定义输出必须是严格 JSON

这部分相对稳定，可先由工程侧固化，再在子 skill 中继承。

### 2.2 子 skill

建议按章节职责拆分：

1. `8d-actor-entity-typing`
2. `8d-d2-event-extraction`
3. `8d-d4-root-cause-extraction`
4. `8d-d5-action-extraction`
5. `8d-risk-extraction`
6. `8d-background-knowledge-extraction`
7. `8d-relationship-normalization`
8. `8d-temporal-normalization`

## 3. 共创优先级

建议按下面顺序与用户共同定义：

### Foundation

`8d-actor-entity-typing` 与 `8d-temporal-normalization`

原因：

- 会影响多个章节 skill 的稳定性
- 能提前避免人名/组织名混淆和时序字段返工
- 属于跨技能公共底座

### Priority 1

`8d-d4-root-cause-extraction`

原因：
- 对图谱价值影响最大
- 也是当前最依赖业务判断的抽取模块
- 后续因果链、审核、自动补边都会依赖它

### Priority 2

`8d-d5-action-extraction`

原因：
- 与根因强关联
- 容易决定关系方向和责任归属

### Priority 3

`8d-relationship-normalization`

原因：
- 直接影响入图质量
- 可以把“抽到了但关系乱”这一类问题尽量收敛在统一模块里

### Priority 4

`8d-d2-event-extraction`

原因：
- 事件字段相对结构化
- 但它会复用前面已经拍板的 actor typing 与 temporal normalization 约束
- 因此前置基础打牢后再细化会更稳

## 4. 每个 Skill 需要共同拍板的内容

每个 skill 建议都按同一模板共创：

### 4.1 输入边界

- 处理哪些章节 / `section_path`
- 处理哪些 `chunk_role`
- 是否允许跨 chunk 汇总
- 是否允许读取表格抽取结果作为上下文

### 4.2 输出边界

- 允许输出哪些实体类型
- 允许输出哪些关系类型
- 哪些字段是“必须抽到”
- 哪些字段抽不到时必须留空而不是猜

### 4.3 证据与置信度

- `supporting_chunks` 的最小要求
- 是否允许 1 个实体对应多个 chunk
- 何时应该降低 `confidence`
- 何时应该直接放弃抽取

### 4.4 业务判断规则

- 否定语义如何处理
- 模糊描述如何归类
- 并列原因 / 并列措施如何拆分
- 同一句里同时出现现象、原因、措施时如何归属

### 4.5 失败策略

- 输出空结果还是部分结果
- 是否允许产出 `warnings`
- 何时触发 fallback provider

## 5. 当前建议的最小灰度替换范围

v0.3 第一阶段不建议全量替换所有抽取模块，建议只让 Codex 接管：

- `RootCause`
- `ActionItem`
- 关系归一化

以下保持现状：

- 表格规则抽取
- 报告基础字段
- 故障清单类字段
- Writer / 审计 / 溯源逻辑

## 6. 下一轮共创建议

建议下一轮先完成 `Foundation` 两项的口径冻结：

1. `8d-actor-entity-typing`
2. `8d-temporal-normalization`

建议先拍板的最小内容：

1. `Person / Organization / Department` 的保守判别规则
2. actor 类字段的双轨输出边界
3. 标准化时间字段与 raw 时间文本的对应关系
4. `timePrecision` 的枚举和使用位置
5. 时间精度不足时的默认策略

这两项定下来之后，再进入 `8d-d4-root-cause-extraction`，后面的 `D2 / D4 / D5` skill 会明显更稳，也更不容易在时序图谱升级时返工。
