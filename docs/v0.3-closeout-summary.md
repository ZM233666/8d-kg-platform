# v0.3 Closeout Summary

**状态**：completed  
**日期**：2026-05-19  
**定位**：本文件总结 `v0.3` 的核心实现结果、关键决策、已解决风险与后续建议。

---

## 1. 本轮达成了什么

`v0.3` 最终完成的是一条可真实运行的、面向 8D 报告的 `Codex` 抽取闭环：

- 本地 `Codex` 服务可由后端真实调用
- `D2 / D4 / D5` 技能模块已接入抽取 runtime
- 章节化拆分已恢复，真实 `.docx` 8D 报告不再按整篇单 chunk 处理
- 图谱关系进入“少连但准”的保守收敛模式
- 时间字段达到“原文明确则写入，否则为空”的最小可查询能力
- 真实 `EP2002` 报告已完成抽取、入图、回查的 live 验证

换句话说，本轮已经把 `v0.3` 从“设计方案”推进到“真实系统能力”。

---

## 2. 关键设计决策

### 2.1 用 Codex skill 链替代单一 LLM 抽取

没有把整份报告交给黑盒 agent 自由发挥，而是采用：

- `8d-report-extraction-core`
- `8d-actor-entity-typing`
- `8d-temporal-normalization`
- `8d-d2-event-extraction`
- `8d-d4-root-cause-extraction`
- `8d-d5-action-extraction`
- `8d-relationship-normalization`

这种模块化 skill 组合方式。

### 2.2 先让 runtime-compatible 能力落地，再逐步追上目标 ontology

本轮没有一次性把 `Person`、raw 时间字段、`timePrecision`、完整 temporal KG 一起推到 runtime。  
相反，采用了：

- 规则先落地
- schema 渐进升级
- 写库和查询先保持稳定

这种保守策略。

### 2.3 图质量优先于图规模

本轮的 writer / relationship normalization 明确采用：

- 白名单关系
- 端点合法性过滤
- 多候选场景不乱补边
- `owner_name` 优先匹配责任组织

因此当前图谱会更瘦，但明显更干净。

### 2.4 时间字段不允许“聪明猜测”

对 `closed_at / completed_at` 的策略是：

- 原文明确出现才写
- 只有状态、计划、顺序词时不推断
- 没有就空

这保证了时间查询的可信度。

## 3. 本轮解决的主要风险

### 3.1 整篇单 chunk 导致路由和溯源失真

问题：

- `s2_split` 一度退化成整篇一个 chunk
- D2 / D4 / D5 边界难以收敛

结果：

- 已恢复章节化拆分
- 并加入子章节 role override

### 3.2 责任组织和封面抬头混淆

问题：

- `克诺尔苏州`
- `Knorr-Bremse Systems for Rail Vehicles (Suzhou) Co., Ltd.`
- `供应商`

这些组织表达在真实报告中容易混成封面公司抬头、责任组织或泛称主体。

结果：

- 已有 alias 归一
- `ActionItem -> RESPONSIBLE_ORG` 已稳定
- `EightDReport -> RESPONSIBLE_ORG` 不再被封面抬头污染

### 3.3 时间字段漂移或过推断

问题：

- 真实报告里常见“关闭”“完成”等词，但不是业务时间字段

结果：

- `closed_at / completed_at` 已改成显式证据驱动
- live 样本已验证“无时间即空”

## 5. 当前边界

`v0.3` 已完成，但不等于系统已经变成完整 temporal KG 或完整 ontology runtime。

当前仍然保留的边界有：

- `Person` 仍在目标层，未完全进入 runtime
- raw 时间字段未正式入图
- `timePrecision` 未正式入图
- 关系级时间有效期未引入
- `.doc` 兼容虽有回退，但未作为本轮主验收对象

这些不是遗漏，而是有意延后。

---

## 6. 后续建议

`v0.3` 结束后，优先做的不是立刻扩新功能，而是继续沉淀资产：

1. 扩充真实回归样本，尤其是带明确关闭时间和措施完成时间的报告
2. 同步更新可复用 skills，把本轮经验沉淀成跨项目方法
3. 清理 `docs/SCHEMA.md` / `docs/PIPELINE.md` 与当前实现的漂移
4. 再决定下一阶段是优先推进：
   - runtime ontology 升级
   - temporal KG 深化
   - 还是前端时序查询能力

---

`v0.3` 已经完成了它最关键的使命：
