# v0.3 Postmortem Risk Backlog

**状态**：active  
**日期**：2026-05-19  
**定位**：记录 `v0.3` 完成节点后的高风险缺陷、隐患与避坑建议，作为 `v0.4` 开工前的修复优先级清单。

---

## 1. 结论摘要

`v0.3` 已达到“功能完成 + 验收通过”的里程碑，但当前仍存在几类会在真实运行中逐步放大的风险：

1. 组织泛称误入图，导致跨报告串图
2. 组织 alias 归一后未去重，导致责任边丢失
3. `VERIFIES_CAUSE` 兜底补边偏宽，导致根因闭环关系被污染
4. formal e2e 目前更像本机 live 验收脚本，而不是团队可复现资产
5. live e2e 会持续污染共享远端环境，长期会降低测试稳定性

因此，`v0.4` 开工前建议先处理“高风险低成本”的防护项，而不是继续无条件扩新功能。

---

## 2. 立即修（P1）

### P1-1 组织泛称不要直接物化为全局 Organization

**现象**

当前 `owner_name` 只要看起来像组织名，就可能被补成正式 `Organization` 节点，例如：

- `供应商`
- `客户`
- `质量部`

由于 Neo4j 按 `business_key` 全局 `MERGE`，这些泛称会把不同报告、不同真实主体错误合并到一起。

**影响**

- `RESPONSIBLE_ORG` 串图
- `SUPPLIED_BY` 串图
- 组织维度统计失真
- 后续 Aligner / Concept Tree 更难收敛

**建议**

- 只有命中 alias 表或满足“足够具体的组织表达”时，才允许物化 `Organization`
- 泛称主体先只保留在：
  - `owner_name`
  - `reporter_name`
  - `supplier_name`
- 不直接入图成规范节点

**建议优先级**：最高

---

### P1-2 canonical alias 归一后必须按 canonical key 去重

**现象**

同一份报告里，如果同时抽到：

- `克诺尔苏州`
- `Knorr-Bremse Systems for Rail Vehicles (Suzhou) Co., Ltd.`

它们会被归一成同一个 canonical key，但对象列表里仍可能保留多个实体实例。

当前 `normalize_action_responsible_org_relationships()` 又要求匹配到的组织必须“恰好一个”，这会让责任边在归一后反而丢失。

**影响**

- `ActionItem -> RESPONSIBLE_ORG` 偶发丢边
- 回归表现不稳定
- 同一报告内部图结构不一致

**建议**

- 在 `normalize_organizations()` 后增加一步：
  - 按 canonical `business_key` 去重
  - 合并 `supporting_chunks`
  - 优先保留更完整的 `org_name / org_type`
- 或至少在责任匹配时按 canonical key 去重，而不是按对象个数判断

**建议优先级**：最高

---

### P1-3 formal e2e 需要一个可提交的最小样本，不要只依赖本地 `docs_for_test`

**当前状态**

- 已完成  
- 已新增基于仓库内 `backend/tests/fixtures/mock_8d_report.docx` 的正式 e2e：
  [backend/tests/test_e2e_fixture_pipeline.py](/Users/God-Prime/Desktop/KnowledgeGraph/8d-kg-platform/backend/tests/test_e2e_fixture_pipeline.py)
- 当前 live e2e 继续保留在：
  [backend/tests/test_e2e_live_pipeline.py](/Users/God-Prime/Desktop/KnowledgeGraph/8d-kg-platform/backend/tests/test_e2e_live_pipeline.py)

**现象**

当前 e2e 用的是本地 `docs_for_test/` 下的真实 `.docx`，但这个目录已被 `.gitignore` 忽略。

这意味着：

- 新环境里测试很可能直接 `skip`
- CI 里不会真正验证 parse → split → extract → write → query 闭环

**影响**

- 看起来“测试是绿的”，实际上没有跑
- 团队无法复现你的验收结果

**建议**

- 补一个可提交的、脱敏后的最小 `.docx` fixture
- 保留当前 live e2e 作为 `integration/live` 测试
- 另加一个 `integration/local-fixture` 级别的正式 e2e

**建议优先级**：最高

## 3. 尽快补防护（P2）

### P2-1 收紧 `VERIFIES_CAUSE` 兜底补边

**现象**

当前只要存在唯一已验证原因，所有 `ActionItem` 都可能自动连到这条原因上。

**影响**

- 预防措施、行政动作、遏制措施也会被误判成“验证根因”
- 根因闭环率、验证覆盖率等指标会虚高

**建议**

- 只对满足以下条件的 action 补 `VERIFIES_CAUSE`：
  - 标题或 supporting chunks 中有“验证 / confirm / verify / 复测 / 再测 / 实验确认”信号
  - 或 action_type 明确属于验证性动作
- 其余 action 不做该兜底补边

**建议优先级**：高

---

### P2-2 live e2e 要隔离测试数据，不要持续污染共享远端环境

**现象**

当前 live e2e 会往共享 PG / Neo4j 持续写入固定 key 的测试数据，而且没有清理。

**影响**

- 多次运行后查询可能出现多条记录
- `single()` 风格断言会越来越脆
- 验收环境逐渐变成“半生产、半测试”状态

**建议**

- 为 live e2e 增加 run-specific namespace / business key
- 测试结束后清理测试图谱和 metadata
- 或引入专用 test project / test owner 隔离

**建议优先级**：高

---

### P2-3 `s2_split` 继续扩真实样本，不要过度相信当前启发式

**现象**

现在的 splitter 已经比整篇单 chunk 好很多，但仍然高度依赖：

- 标题长度阈值
- 标点过滤
- 子标题关键词匹配

**影响**

- 新格式 Word 报告容易把章节误并到上一段
- D2 / D4 / D5 路由质量会继续漂

**建议**

- 用更多真实样本补 regression
- 特别补：
  - 带冒号的标题
  - 超长章节名
  - 导出后标题和正文粘连的 Word
  - 目录页伪标题干扰

**建议优先级**：高

---

## 4. 先记录观察（P3）

### P3-1 runtime schema 与目标 ontology 仍有刻意分层

这是当前有意设计，不是 bug。

仍在目标层、尚未进入 runtime 的包括：

- `Person`
- raw 时间字段
- `timePrecision`
- 关系级时间语义
- 更完整 temporal KG 属性

**建议**

- 不要在 `v0.4` 初期同时推进所有这些项
- 先保持“目标层清晰、runtime 稳定”的分层

---

### P3-2 `.doc` 兼容已可兜底，但还不是主验收资产

这是当前可接受边界，不建议误解为“老 `.doc` 全量稳定支持”。

**建议**

- `v0.4` 里继续把 `.doc` 当增强项处理
- `.docx` 仍然是主验收格式

---

## 5. 推荐处理顺序

如果要在 `v0.4` 开工前做一轮小修，我建议顺序是：

1. `P1-2` 组织归一后去重
2. `P1-1` 泛称组织不再直接物化入图
3. `P1-3` 补一个可提交的最小 e2e 样本
4. `P2-1` 收紧 `VERIFIES_CAUSE`
5. `P2-2` 给 live e2e 加测试数据隔离

这 5 项做完之后，`v0.3` 基线会明显更稳，`v0.4` 的双轨抽取、Aligner 和重抽框架也更容易接上。

---

## 6. 不建议的做法

在处理这些风险之前，不建议：

- 继续放大自动补边范围
- 让更多泛称主体直接入图
- 把 live e2e 当成唯一正式验收资产
- 在没有隔离的共享环境里频繁重复跑正式验收

---

## 7. 结论

`v0.3` 现在不是“不稳定”，而是：

- **主链已通**
- **质量基本可控**
- **但有几处会随着数据量和使用人数增加而放大的结构性隐患**

这份 backlog 的目标，不是推翻 `v0.3`，而是让它成为一个更适合作为 `v0.4` 起点的稳定基线。
